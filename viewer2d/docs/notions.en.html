viewer2d — Notes

A test bench for render2d: a map you can pan and zoom freely, instead of typing --bbox values by hand. A separate project: all it knows of the renderer is its command line.

1. Purpose and architecture

Testing a style means zooming, panning, watching the rule change at 1:15,000. With the command line, every view needs a --bbox computed by hand. The viewer does that computation every time the map moves.

browser                       NiceGUI server (Python)         render2d (C++)
┌────────────────────┐  GET   ┌──────────────────────┐ runs  ┌──────────────┐
│ Leaflet, Lambert   │ ─────► │ /render.png?xmin=…   │ ────► │ --bbox …     │
│ end of a move      │        │ FastAPI route        │       │ --size …     │
│ → extent + size    │ ◄───── │ returns the image    │ ◄──── │ -o view.png  │
└────────────────────┘  PNG   └──────────────────────┘ image └──────┬───────┘
                                                                    │ reads
                                                          .shp, .gpkg, .yaml styles
  • The browser shows the map and tells the server which area it displays, on how many pixels.
  • The server turns that request into a render2d command line and returns the image.
  • render2d does what it already does: read, style, draw.

This is the principle of a WMS server (the OGC's Web Map Service): a "GetMap" request with an extent and a size, an image in return. With no cache and one process per image, it is not built for performance, but for a test bench it is more than enough: under a second for the whole Brussels Region, much less for a neighbourhood.

NiceGUI is built on FastAPI. It offers two ways to answer an address:

Three FastAPI mechanisms do the work for us:

  • The function's parameters become the address's parameters. The request /render.png?xmin=150000&ymin=160000&xmax=155000&ymax=165000&w=1000&h=1000 arrives with xmin = 150000.0 already converted to a number. If a parameter is missing, or if w=abc, FastAPI answers on its own with a 422 error saying which one is wrong.
  • async and asyncio.create_subprocess_exec: while render2d works, the server does not sit blocked; it can answer other requests.
  • A semaphore (asyncio.Semaphore) limits how many render2d processes run at once. Dragging the map quickly can produce several requests in a row: on an 8-core machine, there is no point starting 20.

3. Asynchronous Python

The /render.png route is declared async def and contains awaits. That is what lets a single Python process serve the page, the JavaScript and several images at once, without ever being stuck while a render2d works.

In Python, that waiter is called the event loop. There is only one; it switches from task to task, but only at the places meant for it.

The two keywords

  • async def declares a function that may pause.
  • await marks a pause: "I need to wait for something; deal with the others, and come back for me when it is ready".

Our route contains two:

async with slots:                                                # pause 1: wait for a free slot
    code, report = await asyncio.to_thread(run_render2d, cmd)    # pause 2: wait for render2d to finish

A timeline, with numbers

  1. At 0 ms, the request for image A arrives. render takes a slot, starts render2d in a separate thread, reaches the await and pauses.
  2. At 10 ms, the browser asks for a file (the page, viewer.js). The loop is free: it answers in 2 ms.
  3. At 200 ms, render2d has finished. The loop resumes render just after its await, reads the PNG and sends it.

The trap: a blocking call

The loop switches tasks only at awaits. A call that blocks without await (subprocess.run, time.sleep, a big computation loop) therefore blocks the whole server. Had we written:

code, report = run_render2d(cmd)        # no await: the whole server freezes during the rendering

the file request of step 2 would have waited 200 ms, and the second image would have waited for the first one to finish. That is why run_render2d goes through asyncio.to_thread: the blocking work goes to a separate thread, and the loop waits for its end without blocking.

Concurrency is not parallelism

The loop does one thing at a time: that is concurrency, many things in progress at the same time because, most of the time, we are waiting (for a disk, the network, another program). The real parallel computation, here, is the render2d processes, each on its own core. And the semaphore decides how many there are at once.

In C++, the equivalent of the semaphore is std::counting_semaphore (C++20), and async with plays the role of a lock_guard: the slot is given back automatically when the block is left, even on an error, like RAII.

Demo — four images and one file requested almost at the same time

Assumptions of the demo: each rendering takes 200 ms when it has a core to itself (the machine has 4), a static file 2 ms. Beyond 4 simultaneous renderings, they would share the cores and all slow down.

4. Leaflet in Lambert metres

By default, Leaflet works in Web Mercator, with latitudes and longitudes. Our data are in Belgian Lambert 72, and render2d does not reproject yet. Fortunately, Leaflet has a "simple" coordinate system, L.CRS.Simple, meant for plans that are not maps of the globe (a video game map, a scanned drawing). We put our Lambert metres into it directly:

  • one map unit is one pixel at zoom 0, and north is up;
  • in Lambert, one unit = one metre: at zoom 0, 1 metre = 1 pixel.

The coordinate-order trap

Leaflet always writes a point [lat, lng], that is [y, x], the opposite of what GIS people are used to. The Lambert point (X = 150,000, Y = 165,000) is written [165000, 150000] for Leaflet. We wrap it once and for all in a small function, as Leaflet's documentation advises:

const xy = (x, y) => L.latLng(y, x);       // we think in (X, Y), Leaflet receives [Y, X]

Why not NiceGUI's ui.leaflet?

NiceGUI provides a map component, ui.leaflet, very handy in Web Mercator. But its options go through JSON, and a coordinate system like L.CRS.Simple is a JavaScript object, which JSON cannot carry; its documentation does not mention it. For this Lambert test bench, we therefore write a few dozen lines of JavaScript with Leaflet directly, in the NiceGUI page. Once reprojection exists, we can move to ui.leaflet with an OpenStreetMap background.

5. Leaflet's zoom and our resolution

Each zoom step doubles the display size. At zoom z, one metre is 2z pixels; the resolution, in metres per pixel, is therefore 2−z.

A few values
  1. Zoom 0: 20 = 1 pixel per metre, i.e. 1 m/px, scale 1 ÷ 0.00028 ≈ 1:3,571.
  2. Zoom −2: 2−2 = 0.25 pixel per metre, i.e. 4 m/px, scale ≈ 1:14,286. Just below the limit of the buildings style (1:15,000).
  3. Zoom −4: 2−4 = 1/16 pixel per metre, i.e. 16 m/px, scale ≈ 1:57,143: the whole Region.
  4. Conversely, for the Region at 16.529 m/px: z = −log2(16.529) ≈ −4.05.

So we need negative zooms (minZoom: -6) to see the whole Region, and we allow fractional zooms (zoomSnap: 0) so that the wheel does not jump by powers of 2. The maximum zoom, 3, gives 8 pixels per metre: a 6 m house is 48 pixels.

6. One image per view

After each pan or zoom (Leaflet's moveend event), the page:

  1. reads the visible extent (map.getBounds()) and the map's size in pixels (map.getSize());
  2. builds the address /render.png?xmin=…&ymin=…&xmax=…&ymax=…&w=…&h=…;
  3. lays the image received on the map (L.imageOverlay), exactly on the requested extent.

The extent and the size come from the same window: they have the same shape, and render2d has nothing to widen.

Three details that make the difference

  • No flicker. The old image stays displayed while the new one arrives, and is swapped only once the new one has loaded. During a zoom, Leaflet enlarges the old one: it is blurred for a moment, but there is always something on screen.
  • Stale answers. Moving the map three times in a row sends three requests. They can come back out of order: the first, slower, after the third. So each request is numbered, and any answer that is not the latest is ignored.
  • High-density screens. On a screen whose devicePixelRatio is 2, we request 2 × more pixels in each direction for a sharp image, and display it on the same extent. But everything the style gives in pixels (line widths, points, house numbers) would then look half as big, and the scale would be computed on the image's pixels, not on the ones seen. So the page also sends the ratio, and render2d receives --pixel-ratio: it multiplies every length of the style by that ratio and computes the scale on the pixels seen (chapter 39 of render2d's notes). On a 4K screen set to 150 %, a 9-pixel house number is drawn on 13.5 pixels of the image, and seen at 9.

7. render2d's report in the page

render2d writes a valuable report on its output: the scale, the number of features, the reading and drawing times, the warnings. The viewer must show it under the map, otherwise most of the test bench's value is lost.

The route returns an image, not text. So the report travels in an HTTP header of the response (X-Render2d-Report), next to the image. The page requests the image with fetch, reads the header, shows the text, then builds the image from the bytes received. One request for both.

The report ends with the exact command line that produced the image. You can copy it and replay it in a terminal, for instance to produce the same view as a PDF: the "replayable command line" principle of the tool.

True to the project's principle, a render2d error does not stop the viewer: the route returns the error text (HTTP code 502), the page shows it instead of the report, and keeps the previous image.

8. Configuration, and why the browser only sends numbers

The viewer reads a small viewer.yaml file at start-up:

render2d: /path/to/render2d/build-release/render2d
layers:
  - source: data/UrbISBuildings_04000_CadastralParcels.shp
    style:  ../render2d/styles/parcelles.yaml
  - source: data/UrbISBuildings_04000_Buildings.shp
    style:  ../render2d/styles/batiments.yaml
start:                      # start view, in Lambert 72
  bbox: [148000, 168000, 152000, 172000]

The browser never sends a file name or a piece of command: only six numbers, which FastAPI has already checked. The files and the path of render2d come from the configuration, on the server side. Even for a local tool, it is the right habit: an address that could be tampered with to run any command would be a security hole, and here there is nothing to tamper with.

To change a style, edit the YSLD file and move the map by a pixel: every view starts render2d again, which reads the style again. No need to restart the server. That is what makes the test bench pleasant for tuning a style.

  • Python: the server logic, short and readable. JavaScript: only what must live in the browser (the map).

  • render2d runs in a separate thread (asyncio.to_thread with subprocess.run) rather than with asyncio.create_subprocess_exec: the latter depends on the event loop type, and on Windows it does not work with all of them. The chosen version works everywhere, and the server stays just as available.

10. Tiles, pyramids and tiles2d

In view mode, every move redraws the whole view. The classic remedy is to shift the image and repaint only the strip that was uncovered: after a 200-pixel drag on a 1000 × 800 view, a 200 × 800 strip = 160,000 pixels out of 800,000, i.e. 20 %. Tiles generalise this idea cleanly, and add what strips cannot do: keep what has already been drawn.

The grid and the pyramid

The ground is cut into fixed squares of 256 × 256 pixels. Each zoom level has its grid, and each tile splits into 4 at the next level: it is a pyramid. In Lambert, with L.CRS.Simple (1 m = 1 pixel at zoom 0, chapter 5), a tile at zoom z covers 256 × 2−z metres on a side.

The size of a tile, level by level
  1. Zoom 0: 256 × 20 = 256 m (1 m/px).
  2. Zoom −2: 256 × 22 = 256 × 4 = 1,024 m (4 m/px, just below the buildings style's 1:15,000 limit).
  3. Zoom −4: 256 × 24 = 256 × 16 = 4,096 m (16 m/px, the whole Region).

A tile's address: z/x/y

In L.CRS.Simple, Leaflet computes a point's pixel as (X × 2z; −Y × 2z): the minus sign flips the Y axis, like the renderer's matrix. The tile containing the point is then:

x = floor( X × 2^z ÷ 256)
y = floor(−Y × 2^z ÷ 256)
The Lambert point (149,000; 170,000), at zoom 0
  1. x = floor(149,000 ÷ 256) = floor(582.03) = 582.
  2. y = floor(−170,000 ÷ 256) = floor(−664.06) = −665. The row number is negative: that is normal, Lambert Y is positive and the pixel axis is flipped. Careful: floor(−664.06) is −665, not −664: floor rounds down, so towards the more negative.
  3. Extent in X: from 582 × 256 = 148,992 to 148,992 + 256 = 149,248.
  4. Extent in Y: the pixel rows go from −665 × 256 = −170,240 to −169,984, so Y goes from 169,984 to 170,240. The point (Y = 170,000) is indeed inside.

The tile is called 0/582/-665, and its command is render2d … --bbox 148992 169984 149248 170240 --size 256x256 --background none.

The key point: this address does not depend on where the user is looking. Two overlapping views ask for the same tiles: they can therefore be kept.

The Region is about 16.5 km across. Since the grid does not fall exactly on its edges, we count one extra tile per side.

Each level multiplies the number by about 4: zoom 1 (128 m per tile) alone would add 130 × 130 ≈ 16,900. Orders of magnitude, to be measured: at about 50 ms per tile including process start-up, the 5,709 tiles take 5,709 × 0.05 ≈ 285 s on one core, a little over a minute on four. And at about twenty kilobytes per tile, roughly 5,709 × 20 kB ≈ 115 MB of cache.

The cache, and when it goes stale

Tiles are stored on disk as cache/<key>/z/x/y.png. The key is a fingerprint (a hash) of everything that changes the drawing: the content of the style files, the date and size of the data files, the version of render2d. Edit batiments.yaml: the key changes, writing goes to a new folder, and the old tiles can never be served by mistake. Unused folders just need deleting from time to time.

Alternative: MBTiles, the de facto standard for distributing a pyramid. It is a single SQLite file, with a tiles(zoom_level, tile_column, tile_row, tile_data) table and a metadata table. A well-known trap: MBTiles numbers rows from bottom to top (the TMS convention), the opposite of z/x/y. y must be flipped when writing and reading.

tiles2d: one more command, not a bigger renderer

Tiles do not go into render2d, which stays a command in the GDAL manner: an extent and a size in, an image out. Cutting and caching live in a separate tool, tiles2d, just as gdal2tiles.py is a script built on top of GDAL:

tiles2d --map map.yaml --zoom -4..0 --bbox 143000 160000 160000 177000 --out cache/
  • For each tile, it computes the extent (as in the demo) and calls render2d, in parallel on several cores, with the same semaphore as in chapter 3.
  • It skips tiles already present: it can be interrupted and started again.
  • It reports, in the spirit of the project: tiles computed, empty tiles, errors, time.

Metatiles

Starting one process per 256-pixel tile costs mostly the start-up. A block of 4 × 4 tiles (a 1,024 × 1,024 pixel image) can be rendered at once, then cut: 16 times fewer processes, and the features straddling two tiles are drawn only once, so they always join. It is the technique of OpenStreetMap's tile servers, and it will also prepare the problem of labels cut at tile borders.

A shapefile's spatial index: the .qix file

For each metatile, render2d sets a spatial filter: "only the features touching this rectangle". GDAL still has to know where the features are in the file. A shapefile is first of all a list: the .shp (the geometries), the .shx (where each geometry starts in the .shp), the .dbf (the attributes). Nothing in it is sorted by place.

The .qix is the spatial index, one more file next to the others. It sorts the features in a quadtree: the Region is cut into 4 quarters, each quarter into 4 again, and so on; each cell knows the numbers of the features touching it.

With numbers. A metatile at zoom 0 covers 4 × 256 = 1,024 m on a side, and the Region's buildings file holds 247,625 of them (counted by ogrinfo -so):

  • Without .qix: GDAL reads the 247,625 envelopes one by one and keeps maybe 3,000. That is the case for every metatile, wherever it is: about 1.3 s per metatile (measured below).
  • With .qix: the Region is about 16 km across; cutting into 4 at each level, a cell is 8 km, then 4, 2, 1 km. After 4 levels, GDAL has the few cells touching the metatile and reads only their features: a few thousand instead of 247,625.

Measured with tiles2d on the whole Region, zooms −4 to 0, 8 parallel jobs, before and after creating the two indexes. The time per metatile is computed as: seconds for the level × 8 jobs ÷ number of metatiles.

Zoom 0, 420 metatileswithout .qixwith .qix
Parcels69.9 s → 69.9 × 8 ÷ 420 ≈ 1.33 s14.9 s → 14.9 × 8 ÷ 420 ≈ 0.28 s
Buildings69.3 s → 69.3 × 8 ÷ 420 ≈ 1.32 s14.0 s → 14.0 × 8 ÷ 420 ≈ 0.27 s
Both layers, zooms −4 to 0207.0 s48.7 s, i.e. 4.3 times less

At small zooms, the index helps much less: at zoom −4, a metatile covers 4 × 4,096 m ≈ 16 km, almost the whole Region. It contains almost every feature, and the index has nothing to discard. What remains, about 0.27 s per metatile, is the real work: starting render2d, reading the useful features, drawing them, then cutting and writing the PNGs.

The index is created once, with GDAL's ogrinfo. The name after ON is the layer's, that is the file's name without .shp:

ogrinfo UrbISBuildings_04000_Buildings.shp -sql "CREATE SPATIAL INDEX ON UrbISBuildings_04000_Buildings"

After that, nothing to do: GDAL finds the .qix next to the .shp on its own. Two remarks:

  • The .qix is part of the cache key (with the other files of the shapefile). Creating it changes the key once: the layer starts again in a new folder. The cache cannot know that an index does not change the drawing, and it is better for it to be too cautious than the opposite.
  • If the .shp is replaced by a new version, the index must be rebuilt. The other formats have theirs without anyone thinking about it: a GeoPackage contains an R-tree index, a FlatGeobuf too, and PostGIS uses a GiST index.

That is why tiles2d shows a hint when a shapefile has no .qix.

The server gets smart, without getting complicated

@app.get('/tiles/{key}/{z}/{x}/{y}.png')
async def tile(key: str, z: int, x: int, y: int):
    path = cache / key / str(z) / str(x) / f'{y}.png'
    if not path.exists():                    # not computed yet: compute it and keep it
        async with slots:
            await asyncio.to_thread(render_tile, z, x, y, path)
    return FileResponse(path)

Pre-computation by tiles2d and on-demand computation thus fill the same cache. On the page side, viewer.js replaces the single image with a Leaflet tile layer (L.tileLayer('/tiles/<key>/{z}/{x}/{y}.png')), which also works in L.CRS.Simple: an ideal test bench for seams, before the real Web Mercator tiles that will come with reprojection.

What viewer2d's Tiles mode does

The View / Tiles switch at the top of the page (a NiceGUI ui.toggle, which calls the map's JavaScript) toggles between the single image and the pyramids. In Tiles mode:

  • One Leaflet layer per data layer, at the address /tiles/<layer>/<key>/{z}/{x}/{y}.png. The zoom moves in whole steps.
  • A missing tile is drawn with its whole metatile, as in tiles2d, and kept. Leaflet asks for the 16 tiles of a metatile at once: a lock per metatile (asyncio.Lock) makes the first request draw, and the other 15 wait and then find their file. Without that lock, the same rendering would run 16 times.
  • The keys are watched: every 2 seconds, the page asks /tiles/status. If a style file has changed, so has its key, and the layer switches by itself to the new pyramid (setUrl). A tile requested with a stale key gets code 410: nothing is ever drawn into an outdated folder.
  • A click on the map shows the tile, its metatile, whether it is already cached, and the exact render2d commands that draw it.
  • The grid, the key and the rendering come from tiles2d's code: a pre-computed tile and a tile drawn on demand are the same file, in the same place.

The small ecosystem

render2d    draws       an extent + a size       → an image         (C++)
tiles2d     cuts        a pyramid                → a cache          (Python)
viewer2d    shows       a map in the browser, served by either one

Each storey stays simple, testable on its own, and replaceable without touching the others: another engine in render2d, MBTiles in tiles2d, MapLibre in viewer2d.

11. render2d reads viewer.yaml itself version 1.2

Since its version 0.3.8 (its §57), render2d can read the map from a file: render2d --config viewer.yaml. That file is precisely ours. viewer2d no longer has to copy each layer into the command line.

The command, before and after

before: render2d data/UrbISBuildings_04000_CadastralParcels.fgb
                 --style ../render2d/styles/parcelles.yaml
                 data/UrbISBuildings_04000_Buildings.fgb
                 --style ../render2d/styles/batiments_grands.yaml
                 … (two more layers)
                 --bbox 151624.390 170420.110 152227.860 170727.980 --size 1870x982 --pixel-ratio 1.5 -o map.png

after:  render2d --config viewer.yaml
                 --bbox 151624.390 170420.110 152227.860 170727.980 --size 1870x982 --pixel-ratio 1.5 -o map.png

The command shown under the map becomes readable, and it replays as is in a terminal. render2d's report now starts with the file read and every full path: you can see under the map what was really loaded.

Two readers, one rule

render2d and editor2d now share the same reader, in C++. viewer2d is in Python: it cannot use it, and keeps its own. The risk is well known: two pieces of code reading the same file end up not understanding it the same way. It is reduced in two ways:

  • in View mode, viewer2d no longer reads the layers to draw them: render2d does. viewer2d keeps from the layers only what it needs for Tiles mode and for the page (the names, the warnings);
  • the rule for relative paths is the same everywhere, and tested with the same example on each side: a relative path is read from the file's folder (render2d §57).
  1. The file: /projects/maps/viewer2d/viewer.yaml. Its folder: /projects/maps/viewer2d.
  2. It contains style: ../render2d/styles/parcelles.yaml.
  3. Join them, then ".." goes up one folder: /projects/maps/render2d/styles/parcelles.yaml.

Before version 1.2, a relative path was read from the folder viewer2d was started from, while render2d and editor2d read it from the file's folder: the same line did not designate the same file.

render2d's version

With a render2d older than 0.3.8, --config would be an "unknown option", and every view would fail. At start-up, viewer2d therefore runs render2d --version once and refuses to start, with a clear message, if the version is too old. A clean refusal at launch is better than an empty map with an error on every move.

The two new keys: visible and title

  • visible: false: in View mode, render2d does not draw the layer; in Tiles mode, its box starts unticked.
  • title: Buildings: the name shown at the top of the page and in the Tiles mode layer list, instead of the file name.

Tiles mode does not change

Tiles are made layer by layer (one pyramid per layer, §10), with tiles2d's command: one source, one style. --config draws all the layers together: it is of no use here. And that is good for the cache: its key is still computed on each layer's files, as before.
